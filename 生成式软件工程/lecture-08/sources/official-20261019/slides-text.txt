SLIDE 8

祝贺你，发明了 CI/CD

从“集成地狱”到小步发布


1990s：Kent Beck / XP 推动频繁集成；改动越少，出错后越容易定位。CI 的发展

2000：Fowler / Foemmel 总结 CI；2001：Thoughtworks 开源 CruiseControl，让自动构建持续运行

2010：Humble / Farley 的《Continuous Delivery》系统化 deployment pipeline，把自动验证延伸到发布。原作者介绍


CI 与两个 CD


Continuous Integration：频繁集成到主干，每次集成都自动构建、验证

Continuous Delivery：保持随时可发布，何时上线可以由人决定

Continuous Deployment：通过检查的变更自动上线。两种 CD 的区别

LINKS ['https://martinfowler.com/articles/continuousIntegration.html', 'https://www.martinfowler.com/articles/originalContinuousIntegration.html', 'https://www.thoughtworks.com/about-us/history', 'https://continuousdelivery.com/2010/02/continuous-delivery/', 'https://continuousdelivery.com/2010/08/continuous-delivery-vs-continuous-deployment/']

SLIDE 9

Hook-Based CI/CD

事件发生，执行指定动作


还记得失败的“播放声音”吗？

开发流程中有很多事件节点：commit、push、pull request、……

CI/CD = 为事件配置指定的动作

例如：PR 新增提交，自动运行 Lint 和测试。GitHub Actions 事件 (羊毛，甚至可以养 Claude Code)




检查要放在有约束力的位置


本地 pre-commit 便于及时反馈，但可以被 --no-verify 跳过。Git Hooks

远程检查配合 required checks + 分支保护，才能让失败真正阻止合并。GitHub 分支保护

SLIDE 10

简单的机制，琐碎的业务规则

Pre-LLM 时代，写配置非常劝退


名词吓唬人，但真的就那么简单

任何业务系统都会很琐碎：CI fail 禁止 merge、override、……

两个 PR 单独都绿，合起来却坏了：合并前验证最新组合；忙碌的主干可用 merge queue

测试偶发失败：谁负责修？允许重跑几次？何时隔离？

生产故障要紧急修复：谁能 override？放行后如何留痕、补检查？

新版本先部署，旧任务后完成：如何避免旧版覆盖新版？部署并发控制




今天，只要 Spec 能表达清楚


Agent 可以写配置；失败怎么办、谁有权例外，仍要成为需求的一部分

SLIDE 11

把 CI/CD 写成 Spec

合并的条件


CI 必须要求 Lint 通过、测试通过

PR 有新提交就重新检查；合并前验证它与最新主干的组合

检查失败就禁止合并；将要求落实为分支保护规则，约束直接 push 和绕过检查的权限


发布的条件


通过 CI 后，根据 main 分支生成页面，直接部署到 github.io

main 更新后，对这次提交重新运行 Lint、测试和页面构建

全部成功才部署这次构建的产物；失败则保留上一版。GitHub Pages 工作流



验收时故意制造一次 Lint 错误、一次测试失败：确认真的合不了、发不出

SLIDE 16

Stripe Minions：哪些步骤需要 Agent？

把固定工序写进工作流


Stripe 的 Minions Blueprint 混合两类节点：

实现任务、修复 CI 失败：由 Agent 决定怎么做。

运行 linter、推送分支：直接执行普通代码，不调用模型。




完整 CI 最多跑两轮


先在本地修 lint，再推送、跑 CI；无法自动修复的失败，交给 Agent 再修一次。

第二次推送、CI 后，分支交回人类审查；团队认为继续重试的收益会递减。

SLIDE 17

Anthropic：16 个 Agent 卡在同一个 Bug

有了并行进程，还得有不同的任务


C 编译器实验：16 个 Agent 协作，开始编译 Linux 时却卡住了。

大家先撞上同一个 bug，重复修复、覆盖彼此的改动。




用 GCC 构造可以独立验证的子任务


大部分文件用 GCC 编译，只把不同子集交给新编译器。

失败后把部分文件换回 GCC，逐步缩小导致失败的集合。



不同 Agent 因而能修不同文件暴露的问题：验证方式改变了任务的可分性。

仍需检查文件组合：有些文件分别过关，放在一起却失败。
