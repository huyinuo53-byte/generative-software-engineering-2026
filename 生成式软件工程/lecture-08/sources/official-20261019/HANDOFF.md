## 整合时特别值得保留的增量

1. Ralph 原文强调一轮聚焦一项工作、先查已有实现、把测试“为什么存在”及运行经验写回文件；循环中仍需要有经验的人诊断规格或环境。作者承认更适合greenfield，不能把个人乐观观点当普遍实证。
2. CI 2000原文区分成功构建与每日失败的构建尝试；源码之外构建脚本/配置/数据库定义也须可复现。测试不能证明没有错误。持续交付与持续部署区别已核原作者短文，不用“CI=跑测试、CD=上线”过度压缩。
3. GitHub required checks 配合权限才有门控约束。文档允许 successful/skipped/neutral，被跳过检查也可能呈现可合并结果；因此应检验失败路径和任务是否实际执行。管理员默认可能绕过，merge queue检验最新主干与前序队列的组合。
4. OpenAI经验是知识可发现、应用可观察、边界可机械检查、持续清理；原文同时明确较少阻塞合并门控，不能把“ClosedAI没公开完整配置”改写成“没有CI”。多年架构一致性仍属未知。
5. Stripe完整CI最多两轮后交还人类，任务过程无人监督不等于最后无人审查。它依赖既有的隔离devbox和工具权限控制，不是给本机Agent无限权限的通用建议。**原图中的 Fix CI failures 画为矩形，而正文明确称之Agent节点；不要仅靠形状断言它纯确定性，最好采用文字说明并注明原图示意局限。**
6. Anthropic：并行收益来自GCC参照把失败拆成不同文件子集，仍要处理组合才失败的情形。评价口径：Opus4.6、16 Agent、近2000会话/两周、20亿输入token、1.4亿输出token、近2万美元。x86 16位启动部分依赖GCC，汇编器/链接器未完整自研，效率与成熟度有限，不能说完全替代成熟C编译器。
7. StrongDM：场景留出与satisfaction不是更换名词就自动防作弊；判断仍依赖场景覆盖和评判质量。DTU从API合同与边界案例出发，必须与真实服务对照，不能把任何mock叫作可靠数字孪生。
8. Friendster是亲历工程师回顾：完整副本重放全部写入，按用户分片降低每节点数据与负载；方案未在其Friendster环境推进。不能用一篇回顾解释整个公司的失败，也不能假设分片迁移/跨片查询已解决。
9. Webvan年报的**40%指配送中心**，CFC是低于70%，不是所有设施40%。尚无设施现金流盈利可在印刷页18核对；容量口径见印刷页21/原始SEC文本行1236–1272。Quibi关停信的原因是管理层提出的可能解释，不是确定因果鉴定。

## 文字提取漏掉的讲义图

第13页为六行表，三列“常见问题/自动检查/人工判断”：

- 一写20KB文档 → 文档字数预算、重复段落检查 → 内容是否值得保留。
- 堆细节、造多余抽象 → 重复率、未使用代码检查 → 抽象是否必要。
- 小任务变大重构 → 改动范围白名单、Diff预算 → 超出范围是否批准。
- 代码能跑但读不懂 → Lint、类型检查、复杂度上限 → 命名与设计审查。
- 改测试让失败消失 → 受保护的回归测试、测试删除告警 → 行为变更是否合理。
- 顺手关闭CI规则 → 规则文件变更须指定人批准 → 批准者与开发者分离。

图下注：阈值按项目约定，CI拦住可判定的问题，例外由人批准。此图有教学作用，应保留并在相邻文字讲清机械检查的边界。

第19页是装备化人物插画的Harness隐喻，不能从图片推断DeepSeek实际技术架构。第24页是Token=0、尝试→失败与反馈→重构→未来大学之间断崖的隐喻图，非统计图。
