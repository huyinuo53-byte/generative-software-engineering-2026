最值得学的是：把“什么时候该做什么、做到什么算完成、失败后往哪里走”写清楚，再把能机械判定的部分交给工具。

对象与范围

你称为 Pistachio 的项目，在所给仓库中标名 pstack。本次实时核对得到版本 0.15.30，锁定提交 eb4db2b…，其中有 57 个 SKILL.md，24 个属于 principle 系列。盘点全部技能入口，重点精读路由、设计、验证、维护、反思和新加入的 statechart，未逐个运行所有技能。这是源码分析，不是 pstack 的效果测评。

文中的“源码事实”指该固定提交的规定或实现；“分析”是我的解释；书签功能是贯穿全文的假设案例。没有安装 pstack，也没有修改现有工作流。

01 / 先看整体

它把经验拆成不同职责

初看像一大包提示词，细看会发现几类文件承担不同工作。下面是我对源码的归类，不是仓库官方的分类标准。

入口与流程

poteto-mode 识别任务，指向 Feature、Bug fix、Investigation 等 playbook。回答“这次按哪条路走”。

专项方法

how 理解当前系统；architect 设计；arena 比较方案。回答“这一步怎样做好”。

判断原则

principle-* 提供有条件的判断，如两次同类修补失败后检查共同前提。回答“遇到分岔如何选”。

模板与工具

references/ 细化委派和产物；scripts/ 执行具体检查。回答“要留下什么、怎样复查”。

一次功能开发可能依次调用理解、设计、实现、验证这些方法；不是把 57 份说明一次塞进模型。入口要求应用某条原则前读取它的叶子文件。这样可以少带无关上下文，但仍依赖执行者正确选路和实际阅读。

依据：入口、原则与 playbooks · Feature 流程

也别把图理解成自动运行的软件调用栈。很多连接是 Markdown 中的指令，具体工具、模型、权限仍由运行环境提供。源码中的 disable-model-invocation: true 也提醒我们：不能仅凭 description 写了触发词，就声称这些技能都会自动触发。

02 / 拆解写法

六种把“建议”写成“可执行方法”的方式

① 先写适用边界，尤其是什么时候不用

how 处理“系统怎么工作”，why 处理“当初为什么这样设计”。后者要求寻找提交、讨论等历史证据，避免把今天读代码得出的猜测冒充当年的理由。tdd 则明确限制适用条件：用户明确要求，或存在明显、便宜的局部测试入口；不为小问题强搭庞大测试环境。

写法启发：description 应写“任务情境 + 可交付结果 + 相邻技能边界”。正文再写不适用条件。只有“你是一位资深工程师，请严谨工作”不能帮助 Agent 选对方法。

依据：how：区分复杂度 · why：证据与动机 · TDD 的适用和跳过条件

② 用能观察到的信号触发下一步

architect 并非只说“先设计再开发”。它要求至少两个结构不同的候选，选定后再实现；如果不同位置反复出现同类绕路、调用方必须了解内部细节，便回到设计。单个边界情况不意味着整个架构错误。

principle-attack-the-premise 更具体：两次依赖同一前提的修复失败，先写出那个前提并设计观察来检验，之后才能继续修。

书签例子：保存提示正常、刷新却丢失。两轮都在改按钮样式就该停下来：我们是不是一直假定“数据已经写入存储”？先读取持久数据再判断，别继续修表面症状。

依据：候选与重新设计信号 · 先验证共同前提

③ 规定中间产物，让下一步有东西可检查

architect 输出接口草图和设计理由。理由模板先写调用者如何使用，再推导类型和模块；还要记录接受了什么代价、为何拒绝其他方案。arena 要记录选了哪个候选作为基础、吸收了什么、拒绝了什么，以及合成结果的验证。

为什么有用：“我认真考虑过”无法接着工作；一页有真实调用方式、约束和取舍的设计记录，可以让下一位 Agent 或人检查。模板的价值在于保留决策依据，不在于填满标题。

依据：从调用者体验推导设计 · 比较、整合与输出

④ 把“验证”拆成真实动作与可见后果

create-verification-skill 先查项目怎样启动、用户从哪里操作、有哪些现成工具，再生成项目专属验证技能。它的核心是五部分：

  1. Launch：启动到真正可用，包括必要的初始化。
  2. Doctor：确认驱动的是正确版本、健康且属于本次检查的实例。
  3. Drive：从真实 UI、CLI 或 API 入口执行用户动作。
  4. Evidence：保留动作和结果，连同数据库、文件等实际副作用。
  5. Cleanup：清理本次启动的资源，保留证据。

生成后要亲自按说明跑通一次，再确认清理没有删掉证据。首次只要求验证一个已登记功能，不代表所有功能已经验收。

书签例子：不能只截“已收藏”的提示。要点击收藏、刷新、重新找到该书签并跳到正确段落；再测重复点击会不会出现两条。这比单问“测试通过了吗”更容易判断。

依据：生成并实际执行验证技能

⑤ 写失败出口、维护范围和责任人

maintain-verification-skill 明确区分三种问题：说明过时、验证工具失效、产品真的坏了。只修验证技能自己的目录；如果产品回归，报告问题，不能悄悄把说明改成“本来就这样”。其结果分为 clean（无须改动）、changed（有已验证的修正）、blocked（受阻）。

它还把工作分开：子代理只读源码，协调者统一操作应用，防止多人同时点击同一页面。这是根据共享资源分工，不是默认代理越多越好。

写法启发：每个技能都应该告诉执行者“受阻时留下什么”“能改哪里”“哪类问题必须转交”。否则失败很容易被包装成一个看似完成的产物。

依据：范围、三类问题与结果

⑥ 把技能本身当成要验证的产品

Authoring playbook 要求检查 frontmatter（文件开头的名称、描述等元信息）、引用文件和跨技能链接，强调只保留会改变决策的文字，引用已有方法而不是重复抄写。Eval playbook 再向前一步：给候选正常用户会提出的任务，隐藏评审身份和评分线索，检查真实打开过的文件及最终产物，不接受“我遵守了规则”的自述作为证明。

reflect 则区分两类教训：可以确定性检查的错误交给脚本、lint（自动检查代码规则的工具）或运行时检查；需要判断的教训再改说明并配失败例子。这是一种把经验变成可复查方法的维护机制，不等于自动自我改进。

新加入的 create-formal-verification-skill 还要求用临时的错误代码验证检查能否抓错，随后撤销该改动。maintain-formal-verification-skill 记录检查覆盖的代码和最后同步版本：代码变了，要先确认模型仍描述当前实现，再解释通过或失败。

可迁移的例子：“所有图片都可打开”的检查，应能发现一条故意放错的图片路径。若坏样本仍通过，先修检查器。这个方法不要求我们立刻采用形式化验证；它提醒我们检查本身也需要反例。

依据：验证检查确实会失败 · 重新确认代码与模型对应

依据：技能写作与结构校验 · 从实际行为评估技能 · 反思后的结构检查与批准

03 / 用同一个例子串起来

给课程笔记加书签，会怎样做？

下面是借鉴后的示例，不是本次已开发的功能。每一步都应减少一种具体的不确定性。

步骤先回答什么留下什么
理解：how现在的段落 ID 稳定吗？页面重建会变吗？真实代码位置、ID 来源、现有存储入口。
明确意图只在这台设备使用，还是必须跨设备？产品决定。源码不能替用户选择这个需求。
设计：architect / arena需求已定为单设备：按段落序号存，还是按稳定段落 ID 存？比较笔记重排后的可靠性与改造成本，选一种保存结构。
实现一个小闭环能否收藏一个段落，刷新后回来？可运行的最小路径；先暴露保存、定位问题。
验证：项目专属技能重复点击、删除、旧链接失效怎样表现？真实操作和持久数据证据；未覆盖项单列。
维护与纠错下次笔记重排，旧书签还有意义吗？迁移或失效规则；修改后重验受影响路径。

你不必亲自实现存储层，仍可以判断三件关键事情：是否满足真实需求，是否出现不允许的用户状态，证据是否足够支持“完成”。但性能、安全和数据迁移等复杂判断，仍需要相应工程知识与验证。

04 / 对照课程后的新发现

相似之处背后，真正值得带走的四点

发现一：宽度探索与小步实现，是不同阶段的策略

课程第 05 讲强调先做通小路径，第 08 讲强调探索不同路线。pstack 把它们落在不同环节：设计时比较结构不同的候选；实现与验证时沿可检查的小单元前进。

分析：先明确单设备需求，再低成本比较按段落序号或稳定 ID 保存，选一种跑通“保存→刷新→返回”。“多想几条路”不要求同时造出几个完整产品；“先做小样”也不意味着永远沿第一条路线修补。

依据：第 05 讲 67:33：先做通一条小路径 · 第 08 讲 05:58：每层都有多个候选 · 至少两种结构候选 · 分成可验证的小单元

发现二：PM 能参与的工程判断，比“审界面”更深入

这次源码中新加入的 statechart 很有启发：把模型里的状态翻译成“用户看到什么”，把迁移翻译成“用户做了什么、系统发生什么”。PM 先判断这些行为是否合理，再把规则交给检查工具。

假设的书签规则：保存失败时不能显示“已收藏”；删除后刷新不能重新出现。你可以先确认这两句话，无须先理解全部实现。

用户规则→状态与变化的模型→模型找出反例路径→真实代码复现

TLA+ 可以理解为描述系统状态和变化的形式化语言，TLC 是检查这类模型的工具。模型中的反例意味着某条规则被破坏；它是否代表真实产品缺陷，还必须对照代码或实际操作。statechart 明确要求：无法复现时，先怀疑模型，并说明模型忽略的部分。

分析：一个很有价值的协作界面，是“用户语言的规则 + 可重复的反例”，不只是让 PM 审一份技术方案。这也把课程里的状态、约束与验证连接到了你的日常工作。

依据：面向 PM 的状态图与复现要求 · 第 07 讲 89:49：显式依赖与纠错 · 第 08 讲 40:58：检查状态变化

发现三：好的架构，也在降低 Agent 看漏东西的概率

architect 的设计红旗包含：多个地方写同一状态、多个清单手动同步、调用方可随意触及内部结构。它明确假设下一位贡献者可能只看打开的文件、复制最近例子、选择最容易编译的路径。

分析：模块边界和单一数据来源还有一层 Agent 价值：减少“只改对局部，却改坏整体”的机会。我们的课程索引曾有固定课程列表，新增课程时必须额外适配；这正说明“信息有多份，要靠执行者记得同步”会形成维护负担。是否值得改成自动派生，要看反复发生的频率，本次没有实施改造。

依据：状态归属与手工同步清单 · 以局部上下文贡献者为设计条件 · 第 07 讲 10:51：边界与约束 · 第 08 讲 52:37：代码与文档关系容易丢失

发现四：越能自动生成，越要知道“通过”究竟证明了什么

课程第 07 讲的账本结构能约束记录形式，但不保证输入事实真实。pstack 的验证流程同样要区分：写了“需要验证”、留下一条结论、实际取得支持结论的证据，是三个层次。

在我们第 08 课笔记的历史制作记录中，HTML 已生成，但桌面目录无法展开，浏览器操作发现了问题；另一次把教师板书与投影中的案例归属混淆，需要对照来源画面才能纠正。两种检查各自看到了不同问题。此处是回读旧证据，不是本次重新跑了整门课。

分析：技能不能只有一个模糊的“质量通过”。应分别写明行为可用、来源忠实、用户目标达成等检查。新增检查也应对应真实失败模式，而不是不断增加步骤数量。

依据：第 07 讲 83:08：结构平衡不等于事实正确 · 动作、状态与副作用的证据

本地案例记录：问题关闭记录 · 最初浏览器失败 · 后续浏览器审计。

05 / 保留判断

这些写法有价值，但不宜整包照搬

  • 复杂度门槛不一致。how 倾向简单路径；why 默认广泛调查；Feature 要求设计探索和委派。对一个按钮文案修改，整套流程可能比任务本身更重。我们应按错误代价与不确定性决定深度。
  • 原作者的读者与我们不同。how 的解释模板面向资深工程师。我们需要补上用户场景、术语解释和一个贯穿例子。照搬模板可能得到正确但读不懂的材料。
  • 角色、工具和权限依赖宿主。文件使用 Cursor 的 Task、规则路径、指定模型和外部插件。移植到 Codex 要重新映射工具并实际试跑。尤其不能把原文的自主外部操作、提交和 rebase 习惯当成我们已有的授权。
  • 多模型共识仍可能共同出错。arena 的价值是暴露不同方案及分歧；最终产物仍要验证。源码不能证明投入更多代理在我们的任务上一定更划算。
  • 形式化检查也有范围。模型通过只涵盖模型、假设和检查条件；代码与模型不一致、漏掉业务规则都可能让真实产品仍然出错。不能把 statechart 画出绿色当作整套软件被证明正确。

依据：原模板的目标读者 · 广覆盖及跳过门槛 · 宿主、角色与自主设置 · 合成结果仍需验证

06 / 对我们的具体启发

先把现有工作流写得可判断，再考虑加技能

下面是建议，不是已生效的改动。我们已有课程笔记流程、来源记录和 HTML 审计，不需要为了学习 pstack 再造一套账本。

  1. 用一张“功能验收卡”连接产品与工程。每次功能变更，写用户目标、可见状态、禁止结果、操作路径、证据和未覆盖条件。用现有仓库的真实入口填充。
  2. 把复杂任务分成两类决策。可观测的问题由实验回答，如刷新后数据是否还在；产品取舍由需求回答，如是否需要账号同步。Agent 应先查事实，再把剩余取舍交给你。
  3. 为重复工作维护一份项目专属验证入口。复用已有审计器；增加功能时补对应路径。不要把“页面能打开”扩大成“功能、内容、来源全部通过”。
  4. 先收集失败例子，再改 skill。如果失败能机械判定，优先补检查器；如果涉及理解，补一条带边界的说明和正反例。用几类真实任务比较修改前后结果与耗时，确认收益后才推广。

一份值得借鉴的技能骨架

这是从上述源码归纳的写作检查表，并非仓库原有的统一格式，也不是已安装技能。

字段需要回答的问题书签例子
触发与排除何时用，何时跳过或转交？改保存行为时用；只改说明文字不全量测试存储。
前提与输入需要哪些真实资料、环境和授权？当前构建、测试数据、稳定段落 ID。
有条件的步骤每步消除什么不确定性？先确认是否写入，再查刷新恢复逻辑。
产物与责任谁写、谁审、写在哪里？实现者给变更；验收者检查实际用户路径。
可观察的验收什么结果支持成功，什么反例推翻它？刷新后回到同一段；重复点击不产生重复项。
失败与恢复受阻时保留什么，从哪里继续？保留失败日志；只重试受影响步骤。
边界与清理能改哪里，证据是否保留？只清理本次测试数据，保留操作记录。
技能自身评估怎样知道新写法真的有帮助？正常保存、重复操作、保存失败三类任务，观察实际行为。
自测：Agent 说“已收藏”，测试也全绿，可以验收吗？

还缺上下文。先看测试到底检查了什么。如果只验证提示出现，却没验证刷新后的持久状态，就没证明用户目标。再确认测的是当前版本、真实入口，失败场景是否在约定范围内。也不用无限补测试：验收范围应来自本次目标和风险。

对你最重要的能力，是把“我希望它好用”转换成“这些情况下必须出现什么、绝不能出现什么，以及怎样观察”。pstack 提供了不少把这件事交给 Agent 协作执行的写法；课程帮助我们理解为什么要这样做、哪些地方仍然需要判断。
